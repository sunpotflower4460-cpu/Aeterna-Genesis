Aeterna-Genesis — browser voice interaction audit handoff
Date: 2026-11-06 UTC
Scope: voice input and spoken AI replies in the existing lab conversation UI.
No change to physics, model prompts, provider implementations, scientific gates or experiment acceptance.

Implemented behavior
- Browser SpeechRecognition / webkitSpeechRecognition, Japanese, on explicit button press only. Interim recognition is labelled unconfirmed; only final text is appended to the editable draft. Final result indices are deduplicated within one recognition session. Existing typed edits remain intact.
- Sending is blocked while recognition is starting, running or finalizing. The user stops, reviews/edits the text, then uses the existing send button. No voice event creates or accepts an experiment.
- Browser speechSynthesis / SpeechSynthesisUtterance for completed replies. Manual per-reply playback, stop, selectable installed voice, and playback rate. Optional automatic playback targets newly completed core/external-AI replies, not old history or repeated polling.
- Microphone start cancels spoken output. A new automatic answer waits while input is active. Hidden AI tabs/panels and page visibility changes stop/abort owned voice work; confirmed draft text remains in the existing input state.
- Cancellation/error generations prevent late utterance callbacks from restarting a cancelled queue. Short Unicode-safe speech chunks preserve ordinary numeric/identifier atoms. Empty content is not queued. Code blocks are announced as available on screen; qualifiers, signs, numbers and variable/product notation remain in speech text.
- Speech status changes to playing only on the browser's onstart event. Autoplay errors and an engine that never starts receive a visible fallback message. Unsupported recognition/output and insecure microphone contexts are handled independently.
- A conversation polling fix keeps the cursor behind earlier incomplete/missing IDs, so a later completed colleague message cannot hide the core's final streamed answer and its done flag.

Permissions and processing
Microphone use requires a supported browser and HTTPS or localhost. An HTTP LAN IP such as http://192.168.x.x is not a secure microphone context. Keyboard/OS dictation and normal typing remain usable fallbacks.
The browser/OS speech service may process audio or read-aloud text remotely. This is explained near the controls and in the voice details. The app does not create/store audio recordings or add an audio-upload endpoint. Confirmed text is sent to the existing AI only by the user's send action.
Auto-read, rate and chosen voice URI are stored locally as preferences. Microphone capture never auto-starts. No new voice API key is needed. AI reply generation still depends on the existing AI connection or external-AI bridge.

Limits / integrity
Real microphone capture, acoustic playback, speech recognition accuracy, OS/browser voice availability and physical-device permission prompts were NOT verified in this environment. Actual voices, pronunciation and autoplay behavior vary. This is not a test of a live OpenAI connection or full-duplex streaming voice service.
Speech is an accessibility/input-output aid, not a measurement or evidence source. Numerical statements and code must be checked against the visible answer and raw records when making scientific claims.
no_touch: model equations, initial conditions, solvers, diagnostics, raw evidence, official Rooms and scientific success thresholds are untouched.
tier: measured/observed software behavior only. No new physical discovery, emergence level or claim of transcription accuracy.
8th audit: no completed shape, desired outcome, result-dependent rule or stopping criterion is added. Experiments still require the existing human-accepted validated input card.
determinism: voice writes only draft/preferences/playback state. Original frame bytes and stopped model state remained identical in the browser test.
