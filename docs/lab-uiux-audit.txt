Scope and claims
This is an application/experiment-input workflow change, not a new physical discovery.
Observed/measured software behavior: an external AI or a tool-using council can propose new, bounded initial inputs; the person accepts a card; the existing solver runs the frozen input from t=0 in a separate worker. The parent is preserved.
No emergence level, ladder status, GREEN classification, official Room, or scientific success criterion is changed. No physical effect is inferred from screenshots taken at different simulation times.

Changes
- Human-facing live landing, persistent viewport, visible pause/step controls and actual solver metrics.
- Desktop comparisons and phone experiment selector; independently scrolling question panel.
- Questions include selected experiment(s), current observation packet, declared editable knob ranges, initial recipe and existing research-memory cautions.
- propose_initial produces input cards with before/after values, seed, unverified expectations, and reproducible JSON. It freezes initial input and excludes all runtime interventions. No worker is launched before acceptance.
- Registered model equations are unchanged. Existing explicit runtime branch/perturb operations remain labelled as interventions.
- Concurrent acceptance of one card is serialised; invalid/unknown/non-finite knob inputs and invalid seeds are rejected.
- Unavailable APIs are visibly labelled. Bridge mode saves an observation packet and request for an external AI; it does not manufacture an automatic answer.
- OpenAI-only configuration example and opt-in server credential-file loading; no shell evaluation, secret output or implicit loading.

Limits and outstanding work
- No new API key has been created or saved. The setup picker did not display for the user. Saving to .env.local awaits explicit destination confirmation. Live OpenAI responses and billing have not been verified.
- The browser input card is explicitly sourced as validation; it verifies the external-AI contract, not actual OpenAI generation quality.
- Supported novelty is new numerical inputs within registered model bounds. Arbitrary new equations, boundary types and generated code are not executed. Those require a reviewed model implementation.
- Times advance independently. A paused original and a new child are not a matched-time physical experiment; use time-series/replay and scientific audit for claims.
- Live sessions remain local and git-ignored; use the existing export/replay process for durable research records.
- Research-memory cautions are deduplicated; individual question novelty is not automatically established.
